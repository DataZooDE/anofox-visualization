A turning shop (two lines of four CNC lathes, day and night shifts) scraps too many parts. One lot in six has more than 3 % scrap, and a sixth of the deliveries are at risk. The plant manager has a budget for one fix. **Which lever is worth paying for?**

## What the charts say

The MES has logged 9,984 lots of 400 parts over 26 weeks: shift, operator, supplier, line speed, hours since maintenance, tool wear, spindle temperature, and the parts out of tolerance. Break scrap down by any factor and there is a gap:

- night lots have twice the high-scrap lots of day lots;
- overdue machines have three times as many as those maintained on time;
- lots of **senior operators** have 12 % high scrap, juniors 22 %.

The obvious answer is to put seniors on the night shift, and it's the expensive one. But the factors move together. The day crew is mostly senior. Nights run the line faster to catch up. The maintenance crew works days, so machines on nights wait longer. A chart of one factor shows every factor that rides along with it, so it can't tell you which gap you'd get if you paid for it.

## What the network says

A Bayesian network learned from the same lot records separates **seeing** from **doing**:

| | high scrap |
|---|---|
| no evidence | 17 % |
| *seeing* a senior operator on the lot | 13 % |
| *making* the operator senior, do(operator = senior) | 16 % |
| do(maintenance on time) | 12 % |
| do(line speed normal) | 8 % |

Seeing a senior operator mostly tells you it's a day lot: the network says *day* is 80 % likely, and overdue maintenance less likely. Setting the operator with do() cuts the arc from *Shift*, which stays 50/50, and buys about one point. Maintenance on time and a normal line speed are the levers.

In the dashboard you click a lever's state to observe it, Alt-click (or the chip) to set it, and combine as many as you like. Only the six levers can be clicked; the machine, the defects and the result only react. ⤢ shows the network full size, still clickable.

**What connects what.** Hover a node and its Markov blanket lights up: its parents, its children and their other parents. Click a node's name, then hover another, and the paths between them that are open given your clicks light up. From *Supplier* to *Scrap* there is one path, through the material. Observe the material and it closes: once you know the material, the supplier tells you nothing more.

**What to check first.** Next to the network, the levers are ranked by how much seeing each one on a lot would tell about its scrap, given what you have clicked so far (mutual information). With nothing known, it's the line speed; click it and the ranking moves on.

## Why seeing isn't doing

<figure class="doc-shot">
  <img class="lp-light" src={causalL.src} alt="The causal view: Operator is the treatment X, Scrap the outcome Y, the back-door paths through Shift dashed, Shift ringed" />
  <img class="lp-dark" src={causalD.src} alt="" />
  <figcaption>The operator as the lever: the back-door paths run through the shift, which is the one thing to compare on.</figcaption>
</figure>

Pick a lever and the network is drawn as a causal question: **X** the lever, **Y** the scrap. A dashed arc is on a *back-door path*, a way for the two to hang together that doesn't run through the lever. For the operator that's *Operator ← Shift → Maintenance → … → Scrap*. Comparing lots of the same shift (the ringed node) blocks every back-door path, and what's left is the operator's own effect, the do() answer. The material has no back door, so for it seeing and doing agree. A chart sets each lever's seen effect against its done effect: where the bars differ, the chart credits a lever with its company.

## The cheapest plan for a target

Five levers, each set or left alone, make 32 plans. For each one, the network's answer to *do(all of them)* is one row of the precomputed answers. Put in what each lever costs and a target for high scrap, and the cheapest plan under the target wins. With the example costs:

- the cheapest plans under 10 % are a normal line speed (8 %) or maintenance on time with inspected material (9.5 %);
- senior operators appear in no cheap plan;
- once all material is inspected, buying only from supplier A adds nothing, because the supplier acts on scrap only through the material.

## How the graph was found

<figure class="doc-shot">
  <img class="lp-light" src={graphL.src} alt="The learned graph against the plant's: 17 matching arcs, one extra in amber, the planner's arc solid" />
  <img class="lp-dark" src={graphD.src} alt="" />
  <figcaption>The learned graph against the plant's true one: one extra arc, structural Hamming distance 1.</figcaption>
</figure>

A structure search learned the graph from the lots, with the process order as its only rule. Each arc's strength is how often 200 resamples of the lots found it: thick when always, dashed below a threshold you set. One arc came from a planner: *Line speed → Delivery*, which the data found in only 38 % of the resamples, stays solid as a required arc. Since the plant is simulated, the learned graph can be laid over the true one. 17 arcs match, and one is extra: *Spindle temperature drift → Scrap*, which is real in the data because scrap counts parts, not only defect classes.

## Is it right?

The plant is simulated, so its truth is known: forcing each lever on 400,000 simulated lots says what it really does. The network was learned from the 9,984 lots alone, plus the process order and one arc a planner knows (a faster line ships earlier).

| Lever (high scrap, points) | seen (network) | done (network) | done (true) |
|---|---|---|---|
| normal line speed | −9.7 | −9.2 | −8.4 |
| maintenance on time | −5.5 | −4.9 | −6.1 |
| day shift | −5.7 | −5.7 | −5.9 |
| good material | −3.3 | −3.3 | −3.8 |
| supplier A | −1.4 | −1.4 | −1.9 |
| senior operator | −3.9 | **−0.9** | **−1.4** |

The network ranks the levers as the plant does, and it sees that *senior operator* mostly stands in for the shift. It underestimates maintenance a little. A second draw of the plant, learned the same way and checked once, gave the same ranking.

## How it's built

The network was learned and solved by an inference engine outside the dashboard. The page gets only its **answers**, as Parquet files: the belief of every node and state for each combination of evidence on the six levers (each one unset, observed or set; 21,875 combinations, 380 KB), the learned arcs with their bootstrap strength, and the aggregates the charts show. No probability tables are published, so the drawing has no table on hover.

The dashboard turns the clicks into a key and looks the beliefs up:

```sql
SELECT 'bayes-net'::REQUIRES;

-- the levers: their states, and their place in the key
CREATE TEMP TABLE levers AS FROM (VALUES
  ('line_speed', ['high', 'normal'], 1), ('maintenance', ['on time', 'overdue'], 5), …
) t(node, states, mult);

-- the key: per lever 0 (unset), 1..k (observed) or k+1..2k (set with do())
CREATE TEMP VIEW keys AS
SELECT coalesce(sum((list_position(l.states, e.state)
         + CASE WHEN e.mode = 'do' THEN len(l.states) ELSE 0 END) * l.mult), 0) AS key
FROM evidence e JOIN levers l USING (node);      -- evidence: getvariable('ev') as rows

SELECT 'ev evidence'::SELECT_AS;
SELECT anofox_plot_bayes_net(n,
         arcs := (SELECT list(a) FROM arcs a),
         beliefs := (SELECT list(b) FROM beliefs b),   -- looked up by the key
         evidence := (SELECT list(e) FROM evidence e))
FROM nodes n;                                    -- the non-levers: settable = false
```

A node row with `settable` `false` ignores clicks, so a reader can only ask what the file can answer.
